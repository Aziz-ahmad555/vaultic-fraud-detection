| D27 | 2026-10-08 | Tuning speed | **Cause:** not the tree method (XGBoost 2.0.3 runs `hist` / grow_quantile_histmaker, all 8 threads; B6/FYP-1 also runs hist via XGBoost 2.x's default, so it is unchanged) and not the search space. | D29 | 2026-10-08 | Phase 8 trust | Calibrator chosen by out-of-fold ECE over 5 contiguous folds of validation, then refitted on all of it; Platt is unregularised LR on the logit; isotonic clips outside its range. | D33 | 2026-10-08 | Phase 7 F7 | F7 = MVAF's gate (same inputs, masked softmax, logit-level weighting) trained SimMLM-style: each batch scored with all available views ('more') and after modality dropout 0.25 ('fewer'); loss = BCE(more) + BCE(fewer) + lambda * mean(max(0, l_more - l_fewer)), lambda = 1. Formula as specified by Aziz; the arXiv 2507.19264 abstract (Li, Chen, Han, ICCV 2025) confirms the MoFe principle, but the full paper's exact formulation was not checked, so it is called 'SimMLM-style'. On synthetic data F7 lowers held-out MoFe violations vs MVAF (0.0318 vs 0.0357, seed 0) at equal PR-AUC | Separate expert heads per view as in SimMLM's mixture of experts | Vaultic's views already are the experts (each outputs a calibrated probability); keeping MVAF's gate makes F7 differ from MVAF only by the MoFe objective, which isolates its effect | Default |
| D34 | 2026-10-08 | Phase 4 graph | Entity features (degree, distinct uids, other uids, known-fraud rate per card / email / address / device; two-hop fraud) use exact timestamps, strictly before t, with labels known only when its_time + L <= t. Two-hop fraud is a path count (a fraud sharing two entities counts twice). Components and Louvain communities use only uid, card and device (email domains and addresses are hubs: addr1 has ~300 values) and, in setting C, a daily snapshot of the 30 days before the transaction's day (never the current day); a transaction is counted in the community of its card node. Settings A and B use one static graph of all transactions | Exact distinct two-hop counts; components over all entity types; per-transaction (not per-day) snapshots | Distinct two-hop sets over hub entities and per-transaction graph snapshots are too costly at 590k rows; the daily snapshot is still strictly point-in-time | Default |
